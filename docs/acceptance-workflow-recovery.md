# Optional SDK workflow recovery acceptance

These failure cases are specified before implementation. The checkpoint belongs to the host running the model, while Second Cursor remains the execution and approval authority. Recovery must never infer that a missing response means an action did not happen.

1. Before dispatching each call, persist the goal, ordered history, progress, session/task identity, target identities, and a new operation ID. A storage failure prevents dispatch. The operation ID sent to the runtime must be the exact ID already on disk.
2. Kill the SDK process after a fixture invoice submission is applied but before its response arrives. A new SDK process loads the checkpoint, reconciles that ID in the original session, records the known result, and finishes with exactly one submission. HTTP and MCP must retain the original authoritative session; a different endpoint, transport, task, workflow ID, goal, target configuration, or explicitly supplied session fails closed.
3. Unknown, missing, expired, interrupted, queued, dispatched, or uncertain operation outcomes stop with `recovery_required`. Do not retry the original call, even with the same ID. An expired journal can accept a reused ID as a new mutation. Unjournaled task/session/target control operations also require host recovery after interruption.
4. A known journal result is evidence of a returned result, not proof of semantic success. Preserve its failed/uncertain postcondition. Reject uncertain journal outcomes and uncertain returned results. A known callback failure retains the successful action result rather than causing duplicate input.
5. Discard all remaining calls from an interrupted model turn, recording cancellation responses for their IDs. Reobserve every recorded native/browser target, and show the fresh reads to the adapter before new continuation. Old coordinates, element indexes, and approval decisions cannot be resumed as queued actions.
6. Read the authoritative task lifecycle before continuing and before dispatching new calls. Paused, needs-user, interrupted, completed, failed, or cancelled runtime tasks stop; the loop never resumes them automatically. Current `onApproval` must approve every future call. A denied or throwing approval causes zero dispatch.
7. Preserve a completed workflow result and return it on later invocations without calling the model or repeating tools. Preserve progress and completed history across interruption and a step-limit stop. An adapter or callback exception must not erase the checkpoint.
8. Only one runner can own a checkpoint. Another live owner is refused; a dead local process lock can be recovered. Malformed JSON, unsupported versions, invalid nested fields, oversized records, insecure file permissions, symlinks, or ownership mismatches fail before model execution. Writes use an exclusive temporary file, mode 0600, fsync, and atomic replacement. The parent is mode 0700 when created.
9. Checkpoints are explicitly opt-in, contain task text, tool arguments/results, and potentially screenshots, and must be stored/deleted under the caller's retention policy. Never serialize client objects, bearer tokens, or provider credentials. Reject the runtime bearer token if it appears in checkpoint content. Running without `workflow` retains the existing in-memory API.

Offline verification uses a real loopback HTTP/MCP server, actual SDK transport, deliberate process death/socket loss, independent mutation counters, and disk inspection. Live invoice verification additionally uses real Second Cursor browser controls and an independent fixture ledger. These tests do not establish simultaneous physical human typing or cursor coexistence.

10. Before dispatch, discover native batch targets from flat step fields and nested `args` objects or legacy JSON strings, with nested arguments winning and inherited top-level targets retained. Tab batches pin every step to the top-level browser and tab even if step fields contain other IDs. Extended browser commands use their separate outer-field precedence. On resume, merge the authoritative task's resolved target identities, including actions addressed by `app`, then take a new task read after pending reconciliation before refreshing every target. A target registered while the lost operation completed must not be omitted.
